# 編集画面は動画編集アプリ風のタイムラインを中心にする(2026-10-29 決定)

M1 を触ったユーザーのフィードバックを受けて、編集画面の操作体系を決めた。プレビューのシーク・再生速度・キー操作、タイムライン、画面構成、ズームの持ち方を含む。データ構造(ステップ単位、時刻はステップ内の出力時刻)は [20261026-step-based-model.md](20261026-step-based-model.md) のまま変えない。

## 決定

- 操作感は一般的な動画編集アプリ(Premiere Pro、Final Cut Pro、DaVinci Resolve)に合わせる
- 画面: 左カラムに「プロジェクト」と「ステップ一覧」、中央にプレビューとタイムライン、右カラムに選択中の対象の設定。左右カラムの幅はドラッグで変えられる
- タイムラインのトラックは固定(映像・テロップ・読み上げ・ズーム)。任意のトラック追加や重ね合わせはしない
  - 映像トラックは 1 クリップ = 1 ステップ。サムネイルを並べ、保持を斜線で示す
  - クリップ端のドラッグは In/Out の変更(録画の続き・手前を見せる)。録画の端で止まる。後続のステップは詰めて動く
  - In を動かしたら、ステップ内の要素の時刻を同じ分ずらして映像の中身との対応を保つ
  - 保持は端ドラッグとは別の操作(右クリック「ここで静止」)。保持の端ドラッグで長さを変える
  - テロップ・読み上げ・ズームの開始・終了はドラッグで変える。ステップの外には出せない
  - 目盛り・全トラックで同じ「時刻→ピクセル」変換を使う(別々に描いたシークバーと帯がずれる問題を構造的に防ぐ)。独立したシークバーは置かない
- ズームはステップに属したまま(時刻はステップ内の出力時刻)。UI ではステップを意識させず、作成した時刻のステップに入れる。プレビュー上の右クリックからも作れる
- ステップの並び替えは頻度が低いので、ステップ一覧の右クリックメニューに置く
- プレビューの停止中の表示は、デコードを常に 1 本だけにし、その間の要求は最新 1 件にまとめる。デコード中は、タイムライン用の縮小フレームのうち近いものを仮に表示する
- 再生速度は ×0.5 / ×1 / ×2 / ×3(プレビューのみ)。音声は速度に合わせて高さも変わる
- キー操作

| キー | 動作 |
|---|---|
| Space | 再生/停止 |
| J / K / L | 逆方向/停止/再生。連打で ×2、×3 |
| ← / → | 1 秒移動 |
| Shift+← / → | 1 フレーム移動 |
| ↑ / ↓ | 前/次のステップ境界へ |
| Home / End | 先頭/末尾 |
| Ctrl+K | 再生ヘッドの位置でステップを分割 |
| Delete | タイムラインで選んだ要素を削除 |

## 理由

- 動画編集アプリの操作に慣れた人がそのまま使える
- シーク不具合の原因は計測で確認した。1080p・キーフレーム間隔 10 秒の録画で、1.5 秒のドラッグ中は描画 0 回、ドラッグ後に溜まった 31 回分のデコード(1 回 0.15〜0.4 秒)を順に処理し、最終位置の表示はドラッグ終了の約 7 秒後だった。デコード要求をまとめた後は、ドラッグ中も描画され、最終位置の表示はドラッグ終了の約 0.6 秒後
- トラックを固定にすれば、データはステップ単位のまま保てる(AI からの編集のしやすさを維持)
- ズームを全体の時刻で持つと、前のステップの読み上げが伸びたときに後ろのズームがすべてずれる
- ←→ を 1 秒、Shift+←→ を 1 フレームにしたのはユーザー指定。一般的なアプリ(←→ が 1 フレーム)とは逆

## 不採用案と理由(逆戻りガード)

- **HLS で内部配信してバッファリングする** — HLS はネットワーク配信用の分割形式で、ローカルファイルはもともと任意の位置を直接読める。遅さの原因はデコードで、配信形式では解決しない。分割には再エンコードも要る
- **ズームをプロジェクト全体の出力時刻で持つ** — 読み上げの長さが変わると後ろのズームがずれる(TIM-01 の理由と同じ)
- **ズームを録画(ソース)の時刻で持つ** — 保持・早送り・同じ区間の再利用で対応が曖昧になり、ズーム中の静止と相性が悪い
- **クリップ端を録画の外へ広げたら保持にする** — 録画の続きを見せる通常のトリムと区別できなくなる
- **任意トラックの汎用タイムライン** — C7 に反し、AI からの編集も複雑になる
- **逆方向の実再生(音声付き)** — WebCodecs で逆向きのデコードは重い。J は停止中の表示を時計に合わせて更新する方式にする

## 前提と再検討の条件

- 正確なフレームの更新は 1 回のデコード時間に縛られる(上の環境で毎秒 2〜3 回)。仮表示の縮小フレームで足りなければプロキシ(キーフレーム間隔の短い縮小版)を作る(NF-04)
- ステップをまたぐズームが必要になったら、境界で遷移をはさまずに続ける指定を足す
