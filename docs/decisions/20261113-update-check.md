# 新しい版は GitHub Releases を見て知らせるだけにする(2026-11-13 決定)

配布(GitHub Releases)の新しい版をアプリが知る方法の決定。通信の範囲(C1・NF-03 の例外)、知らせ方、アプリの設定での扱いを含む。

## 決定

- 起動の 3 秒後に 1 回、メインプロセスから `https://api.github.com/repos/mu-777/stepcut/releases/latest` を読む(下書き・プレリリースは GitHub が除く)。タイムアウト 10 秒。失敗(オフライン・制限・404)は何も知らせない
- 今の版(`app.getVersion()`、package.json の version)より新しければ、ヘッダーの下の帯に「新しい版があります: vX.Y.Z」と「ダウンロードページを開く」を出す。入れ替えはしない
- 帯を × で閉じると、その版をアプリの設定(`dismissedUpdate`)に覚え、次からは知らせない。より新しい版が出たらまた知らせる
- アプリの設定の「このアプリについて」(版・ライセンス・GitHub のリンクと同じ区分)に「起動時に新しい版を確認する」(`checkUpdates`。既定オン、有効にする前の確認なし)と「今すぐ確認」を置く
- 自動の確認はパッケージしたアプリだけ。開発中(`!app.isPackaged`)と CLI では確認しない。「今すぐ確認」はどちらでも動く。E2E は `STEPCUT_UPDATE_URL` で確認先をテスト用のサーバーに差し替える
- 送るのは通常の HTTP リクエスト(IP アドレスと `User-Agent: StepCut-update-check`)だけ。利用者・プロジェクトの情報は送らない
- 開くページは GitHub が返した `html_url` が `https://github.com/` で始まるときだけ使い、ほかならリリースの一覧のページを開く

## 理由

- 配布は GitHub Releases だけなので、利用者が新しい版に気づく手段が要る(ユーザーの指示)
- 基本の機能はオフラインのままで、確認は止められる。失敗を知らせないので、オフラインでも邪魔にならない。既定オン・確認なしはユーザーの判断
- 知らせるだけなら依存を足さずに作れ、インストーラー版・ポータブル版の両方で同じに動く。リリースのワークフローの形にも縛られない

## 不採用案と理由(逆戻りガード)

- **自動で入れ替える(electron-updater)** — ポータブル版では使えない。リリースに `latest.yml` を載せる必要があり、署名がないと Windows の警告が出やすい。作りが大きい
- **既定オフ・有効にするときに確認を出す** — 知らせの目的(気づいてもらう)を果たさない。送る情報が版の問い合わせだけなので、確認までは要らない(ユーザーの判断)
- **閉じても起動のたびに知らせる** — 更新しないと決めた人に毎回出て邪魔になる(ユーザーの判断)
- **開発中も自動で確認する** — E2E・開発の起動のたびに GitHub へ通信し、未認証の制限(1 時間に 60 回/IP)にも当たりうる

## 前提と再検討の条件

- リポジトリ名を変えたら `src/main/update-check.ts` の URL を直す(GitHub は旧名の API を転送するが頼らない。旧名 `mu-777/screen-annotator` で配った版はこの転送に頼る)
- 署名付きのインストーラーを配るようになり、手での入れ替えが負担になったら、自動の入れ替えを見直す
